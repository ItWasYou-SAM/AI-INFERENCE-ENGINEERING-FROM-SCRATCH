Chapter [3.1](/learn/m03/compute-vs-memory-bound) compared compute time with memory time. Divide one by the other and the hardware
constants separate out from the kernel's own property:

$$
\frac{T_{\text{compute}}}{T_{\text{memory}}} = \frac{F / P}{Q / B} = \underbrace{\frac{F}{Q}}_{\text{the kernel}} \Big/ \underbrace{\frac{P}{B}}_{\text{the GPU}}
$$

The kernel's ratio is its **arithmetic intensity**, $I = F / Q$, in FLOP per byte. The GPU's ratio is its **ridge point** $I^{*} = P / B$:
about 153 for an A100 and 295 for an H100 in BF16. The rule is simple:

$$
I < I^{*} \Rightarrow \text{memory-bound} \qquad\qquad I > I^{*} \Rightarrow \text{compute-bound}
$$

## Counting rules

- **FLOPs:** a multiply-add counts as 2. A matmul of $[m \times k] \cdot [k \times n]$ is $2mkn$.
- **Bytes:** count what has to cross between HBM and the chip at least once: each input read and each output written. Data reused from
  shared memory or registers does not count again. Use the storage format: 2 bytes for BF16, 1 for FP8, 0.5 for INT4.
- This gives the *best case*, assuming perfect on-chip reuse. Real kernels move somewhat more.

## The intensities that matter

| Operation (BF16 unless noted) | FLOPs | Bytes | Intensity |
|:--|:--|:--|--:|
| Vector add, FP32 | $n$ | $12n$ | 0.08 |
| Elementwise SiLU | $\sim 4n$ | $4n$ | ~1 |
| GEMV: $d \times d$ weights · one vector | $2d^2$ | $\approx 2d^2$ | **≈ 1** |
| Linear layer, $M$ tokens, $d \times d$ weights | $2Md^2$ | $2(2Md + d^2)$ | $\dfrac{Md}{d + 2M} \approx M$ |
| Square GEMM, $n \times n \times n$ | $2n^3$ | $6n^2$ | $n/3$ |
| Decode attention, per KV head | $4 n_{\text{ctx}} d_h g$ | $4 n_{\text{ctx}} d_h$ | $\approx g$ (query heads per KV head) |

Two rows deserve a closer look.

**The linear layer.** Each weight is loaded once and used once per token in the step. With $M$ tokens, the intensity is about $M$ while
$M$ is much smaller than $d$. So the intensity of an LLM's weight matmuls is set by **how many tokens are processed together**: 1 for
single-user decode, the batch size for batched decode, and the prompt length for prefill.

**Decode attention.** Every sequence reads its *own* K and V, and batching does not share them. Each cached value is used by the query
heads that share its KV head: $g = 1$ for classic multi-head attention, $g = 4$ for Llama-3-8B with grouped-query attention, which is
one reason GQA helps decode ([9.2](/learn/m09/mqa-gqa-mla)). Either way, decode attention sits far below any ridge point.

<Callout type="insight" title="One rule of thumb for LLM serving">
  Weight matmul intensity ≈ tokens per step. On an H100, decode stays memory-bound until about 300 sequences share a step, while a 2,000-token
  prefill is compute-bound by a wide margin. Chapter [3.3](/learn/m03/roofline) shows this on a plot; chapter [3.5](/learn/m03/derive-ai-for-7b)
  works it out for a whole 7B model.
</Callout>

## Three ways to raise intensity

1. **Process more tokens per weight load.** Batching in decode raises $M$. This is the single most important lever in serving
   ([10.1](/learn/m10/continuous-batching)).
2. **Move fewer bytes per value.** INT4 weights carry a quarter of the bytes of BF16, so intensity for the same FLOPs is four times higher
   ([Module 12](/learn/m12/number-formats)).
3. **Fuse operations.** Running RMSNorm, then a matmul, then an activation as separate kernels writes and re-reads the activations to HBM
   between each step. Fusing them keeps the intermediates on chip, removing those bytes. FlashAttention is the famous case: it never
   writes the $T \times T$ score matrix to HBM at all ([8.5](/learn/m08/flashattention)).

<Callout type="warning" title="Intensity is about HBM bytes, not all bytes">
  A kernel that re-reads the same tile from shared memory a thousand times still has high intensity, because those reads never touch HBM.
  That is the point of tiling ([6.1](/learn/m06/tiled-matmul)). Conversely, a kernel that spills registers to local memory, or reads with a
  poor access pattern, moves more bytes than the formula says, and its real intensity is lower.
</Callout>

</Callout>
