Every kernel does two things: it **moves bytes** between HBM and the chip, and it **does math** on them. Whichever takes longer sets
the speed. The roofline model turns that observation into a single plot.

## Two ceilings

A GPU has two hard limits:

- **Peak compute** $P$: how many FLOP/s the tensor cores can do. An H100 SXM does about **989 TFLOP/s** in dense BF16.
- **Memory bandwidth** $B$: how many bytes/s HBM can deliver. An H100 SXM delivers about **3.35 TB/s**.

A kernel's **arithmetic intensity** $I$ is the work it does per byte it moves:

$$
I = \frac{\text{FLOPs}}{\text{bytes moved}} \quad \left[\tfrac{\text{FLOP}}{\text{byte}}\right]
$$

The best throughput it can reach is the lower of the two ceilings:

$$
\text{attainable FLOP/s} = \min\left(P,\; B \times I\right)
$$

On a log-log plot that is a slanted line (bandwidth-limited) meeting a flat roof (compute-limited). They cross at the **ridge point**
$I^{*} = P / B$, which is about **295 FLOP/byte** on an H100. Below the ridge the tensor cores sit idle waiting for data.

<Callout type="insight">
  295 FLOP per byte is a lot. A kernel has to reuse every byte it loads about 300 times before the H100's math units become the
  bottleneck.
</Callout>

## Placing an LLM layer on the roof

Take one linear layer, $Y = XW$, with $W$ of size $d \times d$ and $M$ tokens in $X$. Everything is FP16 (2 bytes).

$$
\text{FLOPs} = 2Md^2 \qquad \text{bytes} = 2\,(Md + d^2 + Md) \qquad I = \frac{Md}{d + 2M}
$$

When $M \ll d$, this simplifies to $I \approx M$: **arithmetic intensity is about the number of tokens processed per step**.

- **Decode** produces one token per sequence per step, so $M$ is the **batch size**. At batch 1, $I \approx 1$, and the H100 runs
  at about **0.3%** of peak.
- **Prefill** processes the whole prompt at once, so $M$ is the **prompt length**. At 2,048 tokens, $I \approx 1{,}024$, which is
  compute-bound at 100%.

## What this means for serving

This one plot explains most of the inference stack:

- **Batching is the main lever for decode.** Each extra sequence in a step reuses the same weight bytes, which raises $I$.
  That is why serving engines do [continuous batching](/learn/m10/continuous-batching).
- **Prefill and decode want different things.** Prefill wants FLOP/s. Decode wants bandwidth. That mismatch motivates
  [chunked prefill](/learn/m10/chunked-prefill) and, at scale, [disaggregated serving](/learn/m15/why-disaggregate).
- **Quantization helps decode for free.** INT4 weights move a quarter of the bytes, so $I$ quadruples for the same work
  (see [Module 12](/learn/m12/number-formats)).

<Callout type="warning" title="The catch">
  The batching argument applies to weight matmuls only. Attention over the KV cache is different: every sequence brings its **own** K
  and V, so batching does not raise attention's intensity. As context grows, attention takes a larger share of decode time, and it
  stays memory-bound however large the batch. That is why [the KV cache](/learn/m09/kv-cache-size) gets a whole module.
</Callout>

## Lab: compute the roofline yourself 🟢

```python title="labs/m03/3.3/roofline.py"
def intensity(m: int) -> float:
    return flops(m) / bytes_moved(m)          # 2*m*d*d / 2*(m*d + d*d + m*d)

def attainable(gpu: str, ai: float) -> float:
    peak, bw = GPUS[gpu]
    return min(peak, bw * ai)                  # TB/s * FLOP/B = TFLOP/s
```
