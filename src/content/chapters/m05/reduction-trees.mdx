A **reduction** combines many values into one: a sum, a max, a count. It shows up constantly in LLM inference. Every softmax needs the
max and the sum of a row. Every RMSNorm needs a sum of squares. Every attention score is a dot product, which is a sum. And sampling has to
find the largest logit, or the top k of them.

A CPU does it with a loop: `for (i...) s += x[i]`. That is $n$ steps, each depending on the last. A GPU needs a different shape.

## The tree

Add pairs, then pairs of pairs. 256 values become 128 partial sums, then 64, and so on: one value after $\log_2 256 = 8$ steps. The total
number of additions is still $n - 1$, the same as the loop, so no extra work is done. The work just runs side by side.

The tree changes the *order* of operations, so it needs an **associative** operator: $(a \oplus b) \oplus c = a \oplus (b \oplus c)$. Sum,
max, min, AND and OR all are. Floating-point addition only nearly is, so a tree sum can differ from a loop sum in the last bits (see
[4.5](/learn/m04/races-and-correctness)).

A large array has many blocks, and `__syncthreads` only works within one block ([4.4](/learn/m04/shared-memory-syncthreads)). So the usual
plan has **two passes**: each block reduces its slice to one partial sum, then a second launch reduces the partials.

- **v1, interleaved and divergent.** Thread `tid` works only if `tid % (2*s) == 0`. Busy threads end up scattered through every warp, so
  all warps keep issuing while most of their lanes sit idle ([2.4](/learn/m02/warps-simt-branching)). The `%` is also slow.
- **v2, interleaved and compact.** Pair number `tid` is handled by thread `tid`, so busy threads are packed together and whole warps
  retire. But thread `tid` now touches address `2*s*tid`, and neighbouring lanes hit the same shared-memory banks: the cost moves from
  divergence to **bank conflicts** ([6.4](/learn/m06/bank-conflicts)).
- **v3, sequential addressing.** Fold the top half onto the bottom: `if (tid < s) s[tid] += s[tid + s]`. Busy threads are contiguous and
  so are their addresses. This is the kernel from [4.4](/learn/m04/shared-memory-syncthreads).

## Then: stop wasting the threads

Even v3 wastes threads. Half of them are idle from the very first step, and each thread loads only one element. Two more changes:

- **v4, add during the load.** Each thread loads two elements and adds them before the tree starts. That needs half as many blocks to
  cover the array.
- **v5, grid-stride + `float4`.** Launch only enough blocks to fill the GPU (here 8 per SM) and let each thread walk the array with a
  grid-stride loop ([4.2](/learn/m04/thread-block-grid-indexing)), reading 16 bytes at a time and keeping a running sum in a register. The
  tree then runs once per block at the very end, instead of once every 256 elements.

```cpp
// labs/m05/5.1/reduction.cu, v5
float v = 0.0f;
const float4* in4 = reinterpret_cast<const float4*>(in);
for (int i = blockIdx.x * BLOCK + tid; i < n / 4; i += gridDim.x * BLOCK) {
    float4 q = in4[i];
    v += (q.x + q.y) + (q.z + q.w);       // most of the work: a private, serial sum
}
s[tid] = v;                               // then one shared-memory tree, as in v3
__syncthreads();
for (int stride = BLOCK / 2; stride > 0; stride /= 2) {
    if (tid < stride) s[tid] += s[tid + stride];
    __syncthreads();
}
```

This mixes the two shapes: a **serial** loop inside each thread, where it is cheapest, and a **parallel** tree only across threads. Almost
every fast reduction kernel works this way.

## Measured

A sum reads each byte once and does one addition per 4 bytes, an intensity of 0.25 FLOP/byte. It is completely memory-bound
([3.2](/learn/m03/arithmetic-intensity)), so the goal is to read memory as fast as the GPU can.

```text title="output (RTX 3050 6GB Laptop)"
Sum of 33554432 floats (134 MB), two passes:
  kernel                            time      GB/s         result
  v1 interleaved, divergent     2.168 ms      61.9       33554430 PASS
  v2 interleaved, compact       2.135 ms      62.9       33554430 PASS
  v3 sequential addressing      2.136 ms      62.8       33554430 PASS
  v4 add during load            1.080 ms     124.2       33554430 PASS
  v5 grid-stride + float4       1.053 ms     127.5       33554430 PASS
  CPU (double)                                           33554430

  cudaMemcpy D2D of the same array: 122.7 GB/s (read + write)
```

This is not the textbook result. In the classic version of this exercise (Mark Harris's 2007 slides, on a G80 GPU), each change to the
tree gave a large speedup. Here **v1, v2 and v3 run at the same speed**: across repeated runs they trade places between 60 and 80 GB/s.
On a modern GPU the warp scheduler hides divergence and bank conflicts in such a short tree, as long as other warps have loads to
issue.

What *does* matter is **bytes in flight**. In v1–v3 every block loads 1 KB and then spends 8 barrier-separated steps in the tree, issuing no
loads at all. Giving each thread a second element (v4) doubles the rate at once, and v5 reaches 127 GB/s. That is about as fast as this
GPU reads memory in practice: a device-to-device copy, which also has to write, manages 123.

<Callout type="insight" title="The lesson generalizes">
  For memory-bound kernels, first ask whether there are enough loads in flight to cover memory latency (Little's law,
  [2.5](/learn/m02/occupancy-latency-hiding)). Only then polish the arithmetic. Profilers report this directly as DRAM throughput as a
  fraction of peak ([7.2](/learn/m07/nsight-systems-vs-compute)). Once a kernel is near that number, nothing else will help.
</Callout>

## Where reductions hide in an LLM

| Kernel | Reduction | Over |
|:--|:--|:--|
| Softmax ([5.7](/learn/m05/softmax-kernels)) | max, then sum of exp | each row of scores or logits |
| RMSNorm / LayerNorm ([8.1](/learn/m08/norms-fused-residual)) | sum of squares (and mean) | each token's hidden vector |
| Attention ([8.4](/learn/m08/mha-kernel)) | dot products, then the softmax reductions | each query against all keys |
| Greedy and top-k sampling ([11.1](/learn/m11/sampling-strategies)) | argmax, top-k | each row of logits, over ~128 K vocabulary entries |
| Split-K / FlashDecoding ([9.5](/learn/m09/split-kv-flash-decoding)) | combine partial results from several blocks | one row split across blocks |

Their rows are short (a few thousand elements) and there are many of them, so the usual layout is **one block, or one warp, per row**. The
tree inside that block then runs very often, and making it cheap is the subject of the next chapter.
