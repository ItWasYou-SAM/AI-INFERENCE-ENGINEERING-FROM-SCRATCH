A **prefix sum**, or **scan**, replaces each element with the sum of all the elements up to it:

| | | | | | |
|:--|--:|--:|--:|--:|--:|
| input | 3 | 1 | 7 | 0 | 4 |
| **inclusive** scan | 3 | 4 | 11 | 11 | 15 |
| **exclusive** scan | 0 | 3 | 4 | 11 | 11 |

The exclusive scan is the inclusive one shifted right by one, starting at 0 (the identity). Any associative operator works, not only `+`.

On a CPU, a scan is a loop where each step depends on the one before. It looks like the least parallel thing possible. It isn't.

## Why it matters

A scan answers the question **"where do I write?"**. Suppose each thread produces a variable number of outputs: some keep their element and
some drop it, or some request 3 KV blocks and some request 7. An exclusive scan of the counts gives each thread its starting offset in a packed
output array, with no atomics and in a deterministic order.

In inference this shows up as:

- **`cu_seqlens`.** Variable-length batches pack sequences end to end; the start of sequence $i$ is the exclusive scan of the lengths
  ([9.4](/learn/m09/varlen-cu-seqlens)).
- **Top-p sampling.** Sort the probabilities, take the inclusive scan, and keep tokens until it passes $p$ ([11.1](/learn/m11/sampling-strategies)).
- **MoE routing.** Count the tokens sent to each expert, then scan the counts to get each expert's slice of a packed buffer
  ([14.5](/learn/m14/moe-expert-parallelism)).
- **Stream compaction.** Keep only the elements that pass a test, packed together. The lab does this at the end.

  2. Switch to **Blelloch** and step through the up-sweep. Compare it with the reduction tree in [5.1](/learn/m05/reduction-trees): it's the same tree, with the partial sums kept.
  3. Compare the total additions: 49 against 30. With 16 elements the difference is small; with $n$ elements it is $n \log_2 n$ against $2n$.
</Callout>

**Hillis–Steele** (1986) adds, at step $k$, the element $2^k$ places to the left. After $\log_2 n$ steps every element has seen everything
before it. It uses $n \log_2 n$ additions: more total work than the serial loop, but in the fewest parallel steps.

**Blelloch** (1990) is **work-efficient**. It runs an up-sweep (a reduction tree that keeps its partial sums), sets the root to zero, then
runs a down-sweep that passes prefixes back down the tree. It uses about $2n$ additions in $2 \log_2 n$ steps, and produces an
exclusive scan.

Inside a warp, Hillis–Steele wins: the 32 lanes exist anyway, so the extra additions are free, and a shuffle does each step in one
instruction:

```cpp
// labs/m05/5.4/scan.cu
__device__ int warp_inclusive_scan(int v) {
    int lane = threadIdx.x % 32;
    for (int off = 1; off < 32; off *= 2) {
        int up = __shfl_up_sync(0xffffffff, v, off);   // value from lane - off
        if (lane >= off) v += up;
    }
    return v;
}
```

A block scan is then built the same way as the block reduction in [5.2](/learn/m05/warp-shuffles): scan each warp, scan the warp totals,
and add each warp's offset back.

## Scanning 16 million elements

One block can only scan one tile, so a long array is scanned in three phases:

1. **Scan each tile**, and write each tile's total to a small `sums` array.
2. **Scan `sums`.** It is $n / \text{tile}$ long, so recurse with the same code.
3. **Add** the scanned total of all earlier tiles to every element of each tile.

The lab runs this with four different phase-1 block scans:

```text title="output (RTX 3050 6GB Laptop)"
Inclusive scan of 16777216 ints (67 MB in, 67 MB out):
  phase 1 kernel     tile      time       GB/s
  hillis-steele       512  2.371 ms       56.6  PASS
  blelloch            512  2.431 ms       55.2  PASS
  warp shuffle        512  2.180 ms       61.6  PASS
  4 per thread       2048  2.193 ms       61.2  PASS
  reduce-then-scan   2048  1.626 ms       82.6  PASS
  cudaMemcpy D2D           1.097 ms      122.4  (the floor: read once, write once)
```

The four block algorithms land within 10% of each other, all at **twice** the copy time. Counting memory traffic shows why: phase 1 reads
the input and writes the output, and phase 3 reads the output and writes it again. That is 4 trips through memory, against 2 for the copy.
The block algorithm barely matters, because memory traffic sets the time.

**Reduce-then-scan** reorganizes the phases. Phase 1 only *reads* each tile and writes its total. Phase 2 scans the totals. Phase 3 reads
the input again, scans the tile, adds the offset and writes the result **once**. That makes 3 trips instead of 4, and the measured time
drops by exactly that ratio, from 2.18 ms to 1.63 ms.

<Callout type="insight" title="The production answer: one pass">
  CUB's `DeviceScan` (and `torch.cumsum` on large GPU tensors) uses a **single-pass** scan with *decoupled look-back* (Merrill and Garland,
  2016). Each tile publishes its total as soon as it is known, and the next tile waits only for its immediate predecessors' published values,
  never for a separate pass. It reads the input once and writes the output once, reaching copy speed. It also needs the memory-ordering
  care of the last-block pattern in [5.3](/learn/m05/atomics-and-cas). In real code, call CUB rather than writing your own.
</Callout>

## Stream compaction

Keep the elements with `x > 2`, packed together and in their original order:

```cpp
flags[i] = x[i] > 2;                     // 1. 0 or 1 per element
pos = inclusive_scan(flags);             // 2. pos[i] = how many kept elements up to and including i
if (flags[i]) out[pos[i] - 1] = x[i];    // 3. scatter each kept element to its slot
```

```text title="output"
Compaction (keep x > 2): kept 4195183 of 16777216 in 4.900 ms  PASS
```

At 4.9 ms this is slow: three separate kernels, a full array of flags written and read back, and a scan that makes three trips of its own.
A fused version computes the flags while loading the tile and scatters while writing it, which brings it close to the cost of one scan.
