Shared memory can deliver 32 four-byte words per clock, one to each lane of a warp, because it is built from **32 banks** that work in
parallel. Consecutive 4-byte words go to consecutive banks:

$$
\text{bank}(\text{word index } i) = i \bmod 32
$$

When a warp issues a shared-memory load, each bank can serve **one word per pass**. If several lanes want *different* words from the same
bank, they are served one after another. That is a **bank conflict**. If several lanes want the *same* word, it is read once and
broadcast, which costs nothing.

So the cost of a warp's access is the largest number of *distinct* words requested from any one bank: an **n-way conflict** takes n passes.

For lane $\ell$ reading word $\ell \cdot s$, the number of passes is $\gcd(s, 32)$: stride 2 is a 2-way conflict, stride 8 is 8-way, and any
multiple of 32 puts every lane in one bank.

## Measured

The lab has every lane read `s[lane * stride]` 4,096 times:

```text title="output (RTX 3050 6GB Laptop)"
Each lane reads s[lane * stride], 4096 times; 80 blocks of 256 threads:
  stride  predicted       time vs stride 1
       0        1-way   0.182 ms       1.0x   all lanes read one word (broadcast)
       1        1-way   0.182 ms       1.0x   consecutive words
       2        2-way   0.183 ms       1.0x   every other word
       3        1-way   0.183 ms       1.0x   odd stride
       4        4-way   0.356 ms       2.0x
       8        8-way   0.708 ms       3.9x
      16       16-way   1.412 ms       7.7x
      32       32-way   2.818 ms      15.5x   a column of float[32][32]
      33        1-way   0.183 ms       1.0x   a column of float[32][33] (padded)
```

From 4-way on, time grows exactly with the number of passes: double the conflict, double the time. A column of an unpadded 32-wide tile is
**15.5× slower** than a row. The padded tile is as fast as the best case.

The 2-way conflict costs nothing *here*. The likely reason: even at stride 1, this loop doesn't keep the shared-memory pipeline full,
because issuing each load and add takes time too, which leaves room for one extra pass. In a kernel that saturates shared memory, like the inner loop of
a register-tiled matmul, a 2-way conflict does cost 2×. Treat small conflicts as cheap only after measuring.

## Where conflicts come from

**Columns of 2D tiles.** Any `__shared__ float tile[R][32]` read down a column is a 32-way conflict. This appears in transposes
([4.7](/learn/m04/coalesced-vs-strided)), in matmul when one operand is read along $k$, and in attention when $K$ is read transposed.

**The fix: padding.** Declare `tile[R][33]`. Row $r$ now starts at word $33r$, which is bank $r \bmod 32$, so a column visits all 32 banks.
It costs one wasted column of shared memory.

**The other fix: swizzling.** Instead of wasting memory, permute where each element is stored, typically XOR-ing the column index with
bits of the row index: `tile[r][c ^ (r % 32)]`. Every row is still a permutation of the same banks, and every column lands in different
banks. CUTLASS, FlashAttention and Triton all use swizzled layouts, because tensor-core loads (`ldmatrix`) need tiles with no padding gaps.

<Callout type="insight" title="Wider accesses">
  Lanes reading 8-byte (`float2`) or 16-byte (`float4`) values are processed in groups: a warp's 512-byte `float4` access is split into
  4 phases of 8 lanes, and conflicts only count within a phase. That is why `LDS.128` reads in the 6.2 matmul stay conflict-free even though
  each lane spans 4 banks.
</Callout>
