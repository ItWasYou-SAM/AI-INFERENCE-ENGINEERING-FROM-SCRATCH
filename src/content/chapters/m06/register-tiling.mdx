[6.1](/learn/m06/tiled-matmul) ended with a kernel limited by shared memory. Look at its inner loop:

```cpp
for (int k = 0; k < 32; k++) acc += As[ty][k] * Bs[k][tx];
```

Each iteration is **two shared-memory loads and one FMA**. An Ampere SM can issue 128 FP32 FMAs per clock, but only 32 shared-memory load
lanes per clock. The FMA units spend most of their time waiting.

The fix is the same idea as shared-memory tiling, one level down: **reuse values from registers**.

## The outer product

Suppose a thread computes a $T_M \times T_N$ block of outputs instead of one. At each $k$, it needs a column of $T_M$ values of $A$ and a row of
$T_N$ values of $B$. Every pair multiplies into one output:

$$
\text{acc}[i][j] \mathrel{+}= a_i \cdot b_j \quad \text{for all } i < T_M,\ j < T_N
$$

That is an **outer product**: $T_M + T_N$ loads feed $T_M \cdot T_N$ FMAs.

| Per thread | loads per k | FMAs per k | FMAs per load |
|:--|--:|--:|--:|
| 1 output (6.1) | 2 | 1 | 0.5 |
| 8 outputs in a column (1D) | 9 | 8 | 0.9 |
| 8 × 8 outputs (2D) | 16 | 64 | 4 |

## 1D, then 2D

**1D tiling** gives each thread 8 outputs down one column. A block computes a 64 × 64 tile with 512 threads. Each thread loads one value of
$B$ and reuses it 8 times from a register.

**2D tiling** gives each thread an 8 × 8 square. A block computes a 128 × 128 tile with only 256 threads, and each thread keeps 64
accumulators, 8 values of $A$ and 8 of $B$ in registers:

```cpp
// labs/m06/6.2/register_tiling.cu, mm_2d (inner loop, per k-step of 8)
for (int k = 0; k < BK; k++) {
    for (int i = 0; i < TM; i++) regM[i] = As[(threadRow * TM + i) * BK + k];   // 8 loads of A
    for (int j = 0; j < TN; j++) regN[j] = Bs[k * BN + threadCol * TN + j];     // 8 loads of B
    for (int i = 0; i < TM; i++)
        for (int j = 0; j < TN; j++) acc[i * TN + j] += regM[i] * regN[j];      // 64 FMAs
}
```

Everything here is fully unrolled (`#pragma unroll`), so `acc`, `regM` and `regN` become plain registers. That only works because every
index is known at compile time; an array indexed by a runtime value would be placed in slow local memory instead
([6.3](/learn/m06/register-pressure-spilling)).

## Then: wider loads

Two more changes finish the job:

- **`float4` global loads.** Each thread brings in 16 bytes of $A$ and 16 of $B$ per k-step with one instruction each.
- **Store $A$ transposed in shared memory.** The inner loop reads 8 *consecutive* values of $A$ for one $k$. If $A$'s tile is stored $k$-major
  (`As[k][m]`), those 8 values are adjacent, and the compiler can load them with two 16-byte `LDS.128` instructions instead of eight 4-byte
  ones.

## Measured

```text title="output (RTX 3050 6GB Laptop)"
C = A * B, 4096 x 4096 FP32:
  kernel              time   GFLOP/s  of cuBLAS   regs   blocks/SM  max error
  tiled (6.1)    202.79 ms       678      14.9%     38           1    3.5e-04 PASS
  1D tiling       68.16 ms      2016      44.3%     44           2    3.5e-04 PASS
  2D tiling       46.22 ms      2973      65.3%    145           1    3.5e-04 PASS
  2D + float4     32.04 ms      4290      94.2%    109           2    3.5e-04 PASS
  cuBLAS          30.18 ms      4554     100.0%
```

**1D tiling: 3×. 2D: another 1.5×. Vectorizing: another 1.4×.** The last kernel is about 50 lines of CUDA, running at 94% of NVIDIA's library.

Look at the **regs** column. The 2D kernel needs 145 registers per thread, so only one 256-thread block fits in an SM's 64 K registers. The
vectorized kernel, with fewer address computations, needs 109, and two blocks fit. Registers are a budget shared by every thread on the SM,
and [6.3](/learn/m06/register-pressure-spilling) is about spending it.

<Callout type="insight" title="This is the structure of every fast GEMM">
  cuBLAS, CUTLASS and Triton's matmul all use this hierarchy: a block tile in shared memory, a warp tile, and a thread tile in registers,
  computing outer products. The remaining tricks are double-buffering (loading the next tile while computing this one), swizzled layouts that
  avoid bank conflicts ([6.4](/learn/m06/bank-conflicts)), and tensor cores, which compute a whole 16 × 16 outer-product block per warp
  instruction ([6.7](/learn/m06/tensor-cores-mixed-precision)).
</Callout>

## The last 6%

What is cuBLAS doing that this kernel doesn't?

- **Double-buffering.** While computing on one shared-memory tile, it loads the next. Our kernel waits at a barrier for every load.
- **Warp tiling.** It arranges threads so that each warp covers a compact rectangle, which keeps shared-memory reads conflict-free and lets
  more values be broadcast.
- **Autotuning.** It picks tile sizes per GPU and per matrix shape. Our 128 × 128 tile is tuned to nothing in particular.

For FP32 on CUDA cores that last 6% is rarely worth the effort. The bigger lever is moving to tensor cores ([6.7](/learn/m06/tensor-cores-mixed-precision)).
