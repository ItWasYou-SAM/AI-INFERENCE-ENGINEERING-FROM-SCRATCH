An H100 has 16,896 FP32 lanes. A top server CPU has about 96 to 192 cores. Both are made on similar processes with tens of billions
of transistors. So why doesn't someone just put 10,000 CPU cores on a chip?

## Where a CPU core's transistors go

A modern CPU core runs a **single thread** as fast as it possibly can. Very little of its area does arithmetic. Most of it exists to keep
that one instruction stream from ever waiting:

- **Out-of-order execution.** Hundreds of instructions in flight, reordered on the fly so independent ones run while others wait.
- **Branch prediction.** Guess which way each `if` goes, long before the condition is known, and speculatively run ahead.
- **Large caches.** Megabytes of L1, L2 and L3 per core, so that most loads return in a few nanoseconds instead of ~100 ns from DRAM.
- **Wide decode and rename logic, prefetchers, store buffers**, and the bookkeeping to undo every wrong guess.

All of that machinery attacks one problem: **latency**. It makes a single chain of dependent instructions finish sooner.

<Callout type="insight">
  A CPU core is mostly a latency-hiding machine with a small calculator attached. Copy it 10,000 times and you copy the latency-hiding
  machinery 10,000 times too. You would run out of area and power long before you ran out of useful work for it.
</Callout>

## The power wall

Until the mid-2000s, each process shrink made transistors faster *and* lower-power at the same time (**Dennard scaling**), so clocks
kept rising. Then leakage current stopped voltage from falling with size, and since dynamic power grows roughly as

$$
P \propto C\,V^2 f,
$$

raising $f$ meant raising $V$, and power went up much faster than speed. Clocks have sat around 3–5 GHz ever since. More transistors kept
arriving, but they could no longer be spent on making one thread faster. The only way to use them was **more parallel units**, each simpler
and slower than a CPU core, running at a power level the chip can cool.

## The GPU's bet

A GPU spends its transistors the other way round:

| | CPU core | GPU streaming multiprocessor (SM) |
|:--|:--|:--|
| Goal | finish one thread soon | finish many threads per second |
| Hides memory latency with | big caches, speculation, reordering | switching between thousands of waiting threads |
| Arithmetic per unit | a few wide SIMD units | 128 FP32 lanes + 4 tensor cores |
| Instruction control | per thread | shared by 32 threads (a **warp**, [2.4](/learn/m02/warps-simt-branching)) |
| Count on chip | ~100 | 132 SMs on an H100 |

The GPU drops speculation and most of the cache, and shares one instruction decoder across 32 lanes. In exchange it fits far more
arithmetic per square millimetre and per watt. An H100 reaches about **67 TFLOP/s** in plain FP32 and **989 TFLOP/s** in BF16 on its tensor
cores. A large server CPU manages a few TFLOP/s.

<Callout type="warning" title="The price of the bet">
  A single GPU thread is **slow**: no speculation, little cache, and a clock under 2 GHz. A GPU only wins when there are tens of
  thousands of independent pieces of work to keep its lanes busy. The rest of this module is about what "enough parallel work" means,
  and Chapter [4.8](/learn/m04/when-not-to-use-a-gpu) covers when there isn't enough.
</Callout>

## Why this matters for inference

An LLM forward pass is almost entirely matrix multiplication: billions of independent multiply-adds per token
([1.2](/learn/m01/inside-a-transformer-layer)). That is exactly the work a throughput machine is built for. But generation also has a
strictly sequential outer loop ([1.4](/learn/m01/autoregressive-generation)), and each step has to fetch every weight from memory. The
GPU's huge arithmetic rate only helps if the data arrives fast enough, which is the subject of [2.3](/learn/m02/bandwidth-and-memory-hierarchy)
and [2.6](/learn/m02/memory-wall-hbm).
