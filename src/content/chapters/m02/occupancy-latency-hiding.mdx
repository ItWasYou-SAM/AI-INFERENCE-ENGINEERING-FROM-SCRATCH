A load from HBM takes several hundred cycles ([2.3](/learn/m02/bandwidth-and-memory-hierarchy)). A CPU core would cover that with caches
and speculation. A GPU does something simpler: it **switches to another warp**.

## Switching costs nothing

Each SM has four **warp schedulers**. Every cycle, each scheduler looks at the warps assigned to it, picks one whose next instruction is
ready, and issues it. A warp waiting on a load is simply skipped. Because each warp's registers stay in the SM's huge register file the
whole time, switching takes zero cycles: there is no state to save or restore.

So latency is hidden if, at every cycle, *some* warp has work ready. That depends on two things:

- how many warps the scheduler has to choose from, and
- how much independent work each warp does between memory waits.

## Occupancy

**Occupancy** is the number of warps resident on an SM, as a fraction of the maximum (64 on an H100). It is capped by whichever resource
runs out first:

| Resource per SM (H100) | Limit | Used by each block |
|:--|--:|:--|
| Warp slots | 64 warps (2,048 threads) | threads per block ÷ 32 |
| Block slots | 32 blocks | 1 |
| Registers | 65,536 × 32-bit | registers per thread × threads per block |
| Shared memory | up to 228 KB | whatever the kernel declares |

A kernel with 256 threads per block that uses 64 registers per thread needs 16,384 registers per block, so only 4 blocks fit: 32 warps, or
**50%** occupancy, limited by registers.

<Callout type="try" title="Try these">
  1. Start at 256 threads and 64 registers (50%). Drop to 32 registers. Occupancy doubles to 100% and the scheduler gets busier.
  2. Raise **math between loads** to 40 cycles with occupancy at 50%. The scheduler gets nearly as busy as with twice the warps: more work per warp substitutes for more warps.
  3. Set shared memory to 100 KB per block. Only 2 blocks fit, and shared memory is now the limit.
</Callout>

## Little's law: count the bytes in flight

How much has to be in flight to keep HBM busy? **Little's law** says

$$
\text{bytes in flight} = \text{bandwidth} \times \text{latency}.
$$

For an H100, $3.35\ \text{TB/s} \times {\sim}300\ \text{ns} \approx 1\ \text{MB}$ across the GPU, or about **7.6 KB per SM** at every moment.
If each warp has one 128-byte load outstanding, an SM would need about 60 warps to cover that, nearly full occupancy. If each warp has
eight 16-byte-per-lane loads outstanding (4 KB), two warps are enough.

<Callout type="insight" title="Occupancy is a means, not the goal">
  What you need is enough **independent memory requests and instructions in flight**. Many warps is one way to get them. Another is
  **instruction-level parallelism** inside each warp: issue several independent loads before using any of them, use wide vector loads, or
  use asynchronous copies into shared memory. High-performance GEMM and attention kernels often run at 12–25% occupancy on purpose: they
  spend registers on big tiles that give each warp lots of reuse ([6.3](/learn/m06/register-pressure-spilling), [6.6](/learn/m06/latency-hiding-ilp)).
</Callout>

## Lab: an occupancy calculator 🟢

```python title="labs/m02/2.5/occupancy.py"
limits = {
    "warps": SM["max_warps"] // warps_per_block,
    "blocks": SM["max_blocks"],
    "registers": SM["regs"] // (regs_per_thread * threads_per_block),
    "shared mem": SM["smem"] // smem_per_block,
}
blocks = min(limits.values())
```

The last line is the important one: with only one load in flight per warp, even full occupancy can't hide a 500-cycle latency. Real
kernels close the gap with more loads in flight per warp.
