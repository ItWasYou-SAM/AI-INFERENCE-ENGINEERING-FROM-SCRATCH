The 32 threads of a warp execute each load instruction together ([2.4](/learn/m02/warps-simt-branching)). The memory system doesn't fetch
32 separate 4-byte values. It looks at all 32 addresses, works out which **32-byte sectors** of memory they fall in, and fetches each
sector once.

## Coalescing

If lane $i$ reads `x[i]`, the 32 floats are adjacent: 128 bytes in 4 sectors. Every byte fetched is used. This is a **coalesced** access.

If lane $i$ reads `x[8*i]`, each float lands in its own sector. The hardware fetches 32 sectors, 1,024 bytes, to deliver 128 useful bytes.
Seven-eighths of the bandwidth is wasted.

$$
\text{efficiency} = \frac{\text{bytes the warp asked for}}{\text{sectors fetched} \times 32}
$$

<Callout type="try" title="Try these">
  1. Compare **x[i]** and **x[i + 1]**. Misalignment costs one extra sector: 80% instead of 100%. Usually fine.
  2. Try **x[2 * i]**, then **x[8 * i]**. Efficiency halves, then drops to 12.5%, and stays there for larger strides.
  3. Try the **gather**. Each lane fetches its own sector, just like a large stride. Embedding lookups and paged-KV block tables look like this.
</Callout>

## Measured

The lab reads with a stride and writes coalesced:

```text title="output (RTX 3050 6GB Laptop)"
Strided read, coalesced write (128 MB each way):
  stride      GB/s  useful bytes per 32-byte sector
       1     157.9  32 of 32
       2     106.1  16 of 32
       4      64.6   8 of 32
       8      35.8   4 of 32
      16      35.8   4 of 32
      32      35.8   4 of 32
      64      35.8   4 of 32
```

Stride 1 reaches 158 GB/s, close to this GPU's ~168 GB/s peak. From stride 8 on, every lane is in its own sector and the rate settles at
36 GB/s, **4.4× slower** for the same work. (It doesn't fall the full 8× because the writes stay coalesced and the caches help a little.)

## The classic case: transpose

Transposing a matrix reads rows and writes columns, or the reverse. One side must be strided. The fix is to go through shared memory: read a
32 × 32 tile with coalesced row reads, `__syncthreads()`, then write it out as coalesced rows of the transposed tile.

```cpp
// simplified from labs/m04/4.7/coalescing.cu (which loops over 4 rows per thread)
__shared__ float tile[32][33];                 // +1 column avoids bank conflicts (6.4)
tile[ty][tx] = in[(y0 + ty) * N + x0 + tx];    // coalesced read of a row
__syncthreads();
out[(x0 + ty) * N + y0 + tx] = tile[tx][ty];   // coalesced write of a row of the transpose
```

```text title="output"
Transpose 4096 x 4096 floats:
  naive    2.073 ms    64.7 GB/s  PASS
  tiled    0.876 ms   153.3 GB/s  PASS
```

The tiled version is **2.4× faster** and runs near peak bandwidth. Shared memory acts as a reorder buffer: the strided access happens on chip,
where it is cheap.

<Callout type="insight" title="Layout is a performance decision">
  Where possible, choose data layouts so that the dimension a warp walks along is contiguous in memory. In inference this shows up everywhere:
  the KV cache is laid out so that each head's vectors for consecutive tokens can be read in long contiguous runs; paged KV caches use
  blocks of 16 or more tokens so that each gather still reads contiguous chunks ([9.3](/learn/m09/paged-attention)); quantized weights are
  repacked offline into the order the kernel reads them ([12.4](/learn/m12/w4a16-kernel)).
</Callout>

## Other tools

- **Vector loads.** Reading `float4` (16 bytes per lane) issues fewer, wider requests: one instruction moves 512 bytes per warp.
- **Structure of arrays.** An array of structs `{x, y, z, w}` makes a warp reading only `x` stride by 16 bytes. Separate arrays for each field
  keep each read coalesced.
- **Let the profiler tell you.** Nsight Compute reports sectors per request for every load: 4 for coalesced 4-byte loads, up to 32 for the worst case ([7.2](/learn/m07/nsight-systems-vs-compute)).
