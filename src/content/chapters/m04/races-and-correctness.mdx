Suppose every thread checks one element and, if it is positive, adds one to a shared counter:

```cpp
if (x[i] > 0) (*count)++;
```

On a CPU with one thread this is fine. On a GPU it is a **data race**.

## Why it breaks

`(*count)++` is three steps: **read** the counter into a register, **add** one, **write** it back. Thousands of threads do this at once:

| Time | Thread A | Thread B | count in memory |
|:--|:--|:--|--:|
| 1 | read → 5 | | 5 |
| 2 | | read → 5 | 5 |
| 3 | add → 6 | add → 6 | 5 |
| 4 | write 6 | | 6 |
| 5 | | write 6 | **6** (should be 7) |

One increment is lost. With millions of threads, almost all of them are:

```text title="output (RTX 3050 6GB Laptop)"
Counting positives among 16777216 elements (expected 5592406):
  naive    count =      5281  (WRONG)    0.413 ms
  atomic   count =   5592406  (correct)    0.441 ms
  block    count =   5592406  (correct)    0.413 ms
```

The naive kernel counted 5,281 out of 5.6 million: over 99.9% of the increments were lost. Note that it didn't crash or warn. Races produce
plausible-looking wrong numbers.

## Atomics

An **atomic** operation makes the read-modify-write indivisible: the memory system performs it as one step, so no other thread can slip in
between.

```cpp
if (x[i] > 0) atomicAdd(count, 1);
```

CUDA provides `atomicAdd`, `atomicMax`, `atomicMin`, `atomicExch`, and `atomicCAS` (compare-and-swap, which can build any other atomic,
[5.3](/learn/m05/atomics-and-cas)). They work on global and shared memory.

## Contention, and how to avoid it

When millions of threads hit **one** address, the atomics serialize on it. Two standard fixes:

- **Aggregate per block.** Count into a `__shared__` variable (shared-memory atomics are cheap), then do one global `atomicAdd` per
  block. 65,536 global atomics instead of 5.6 million.
- **Aggregate per warp.** Combine the 32 lanes' contributions with warp shuffles ([5.2](/learn/m05/warp-shuffles)) and let one lane do the atomic.

In the lab, the plain atomic version is barely slower than the others. The likely reason is that the compiler already applies warp
aggregation to this simple pattern (every lane adding 1 to the same address) on its own. With more complex updates, such as a histogram where lanes hit different addresses, it can't, and explicit
aggregation can matter a lot ([5.5](/learn/m05/histograms-privatization)).

<Callout type="insight" title="Atomics make floating-point sums non-deterministic">
  Floating-point addition is not associative: $(a + b) + c$ can differ from $a + (b + c)$ in the last bits. With `atomicAdd` on floats, the
  order of additions depends on which threads happen to arrive first, so the same input can give slightly different sums on each run. In an LLM
  this can flip a near-tie between two tokens, which is one reason the same prompt can produce different outputs at temperature 0. Kernels that
  need bit-exact reproducibility use fixed-order reductions instead of atomics.
</Callout>

## Tools: let the machine find bugs

`compute-sanitizer` ships with the CUDA toolkit and runs your program under instrumentation:

| Tool | Finds |
|:--|:--|
| `compute-sanitizer ./app` (memcheck) | out-of-bounds and misaligned accesses, use of freed memory |
| `--tool racecheck` | races on **shared** memory, such as a missing `__syncthreads` ([4.4](/learn/m04/shared-memory-syncthreads)) |
| `--tool synccheck` | invalid barrier use, such as `__syncthreads` in divergent code |
| `--tool initcheck` | reads of uninitialized device memory |

racecheck does not detect races on global memory like the counter above; those you prevent by design. Run your kernels under the sanitizer
at least once, on small inputs: it is slow, but it finds bugs that would otherwise show up as rare wrong answers in production.
