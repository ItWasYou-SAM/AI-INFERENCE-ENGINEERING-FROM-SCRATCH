In [4.1](/learn/m04/kernels-are-not-functions) a launch returned after 4.6 µs while the kernel ran for 5 ms. Here is what happens in between.

## Anatomy of a launch

1. **CPU, your code:** `kernel<<<grid, block, smem, stream>>>(args)`.
2. **CPU, CUDA runtime and driver:** check the arguments, pack them, and write a launch command into a **queue** in memory the GPU can read.
   This takes a few microseconds of CPU time, and the call returns.
3. **GPU front end:** reads commands from the queue in order and, once the previous work in the same stream is done, hands the blocks to the SMs.
4. **SMs:** run the blocks. When the last one finishes, the next command in the stream can start.

So the CPU and GPU run side by side, connected by a queue. As long as the CPU stays ahead, the GPU never waits.

## Launch overhead

The lab launches 20,000 empty kernels:

```text title="output (RTX 3050 6GB Laptop)"
1) 20000 empty launches: 2.72 us per launch
2) same kernels via a CUDA Graph: 0.64 us per kernel
```

2.7 µs sounds small. But a decode step of an 8B model runs several hundred kernels (norms, matmuls, attention, activations, for each of 32
layers), and at small batch many of them finish in a few microseconds. If the CPU needs 2.7 µs to launch a 3 µs kernel, the GPU spends
much of the step idle, waiting for the next command. Decode becomes **overhead-bound** ([3.1](/learn/m03/compute-vs-memory-bound)).

## CUDA Graphs

A **CUDA Graph** records a whole sequence of launches once, then replays it with a single call. The driver has already validated and packed
every command, so replay costs far less per kernel: 0.64 µs instead of 2.72 µs in the lab, and the CPU is free during the replay.

<Callout type="insight" title="Why every serving engine uses graphs">
  vLLM and SGLang capture the decode step as CUDA Graphs for a set of common batch sizes at startup, then replay the matching one each
  step. The catch: a graph fixes shapes and memory addresses at capture time, so engines pad batches to the nearest captured size and use
  pre-allocated buffers. Chapter [8.7](/learn/m08/torch-compile-cuda-graphs) builds this.
</Callout>

## Streams

A **stream** is one of those queues. Work in the same stream runs in order. Work in **different** streams may run at the same time, and
the GPU has separate engines for computing, copying host-to-device and copying device-to-host. So with several streams, one chunk's kernel can
run while the next chunk is copied in and the previous one is copied out.

Three requirements:

- Use `cudaMemcpyAsync` with a stream argument, not `cudaMemcpy`.
- The host memory must be **pinned** ([4.3](/learn/m04/host-device-memory)), or the copy silently becomes synchronous.
- Split the work into chunks, each with its own stream.

## Synchronization points

These all make the CPU wait for the GPU:

- `cudaDeviceSynchronize()`, `cudaStreamSynchronize(s)`, `cudaEventSynchronize(e)`
- `cudaMemcpy` (the non-async one), and any device-to-host copy that needs the result
- In PyTorch: `.item()`, `.cpu()`, `.tolist()`, `print(tensor)`, and data-dependent Python control flow on GPU values

Each one drains the queue. The GPU finishes, then waits idle while the CPU decides what to do next.

<Callout type="warning" title="The decode loop's hardest sync">
  Each decode step must know the sampled token before it can start the next step, and the scheduler must know which requests have finished.
  Modern engines keep the CPU a step ahead: they schedule step $t+1$ while the GPU runs step $t$, and they keep sampling on the GPU so only token
  ids cross the bus ([10.5](/learn/m10/vllm-v1-architecture)).
</Callout>
