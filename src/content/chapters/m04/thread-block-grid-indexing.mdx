A launch creates a **grid** of **blocks**, each a group of **threads** ([4.1](/learn/m04/kernels-are-not-functions)). Inside the kernel, four
built-in variables describe where a thread sits:

| Variable | Meaning | Type |
|:--|:--|:--|
| `threadIdx` | this thread's position inside its block | `uint3` (x, y, z) |
| `blockIdx` | this block's position inside the grid | `uint3` |
| `blockDim` | threads per block in each dimension | `dim3` |
| `gridDim` | blocks per grid in each dimension | `dim3` |

## The 1D formula

$$
i = \texttt{blockIdx.x} \times \texttt{blockDim.x} + \texttt{threadIdx.x}
$$

Block 0 covers indices $0 \dots \texttt{blockDim}-1$, block 1 the next stretch, and so on. To cover $n$ elements you need
$\lceil n / \texttt{blockDim} \rceil$ blocks, which is usually written `(n + threads - 1) / threads`. The last block is usually only partly
needed, so every kernel guards with `if (i < n)`.

## Grid-stride loops

Instead of launching one thread per element, you can launch a fixed grid (a few blocks per SM) and let each thread walk through the array:

```cpp title="labs/m04/4.2/indexing.cu"
__global__ void scale(float* x, float s, int n) {
    int stride = gridDim.x * blockDim.x;                  // total threads in the grid
    for (int i = blockIdx.x * blockDim.x + threadIdx.x; i < n; i += stride)
        x[i] *= s;
}
```

The same launch works for any $n$, and each thread amortizes its setup over several elements. In the lab, 20,480 threads correctly cover 10
million elements.

## Two dimensions

For matrices and images, 2D blocks are more natural. With a row-major matrix (element $(r, c)$ at `r * cols + c`):

```cpp
int col = blockIdx.x * blockDim.x + threadIdx.x;   // x -> columns
int row = blockIdx.y * blockDim.y + threadIdx.y;   // y -> rows
if (row < rows && col < cols) c[row * cols + col] = a[row * cols + col] + b[row * cols + col];
```

<Callout type="warning" title="Put x on the contiguous dimension">
  Threads are grouped into warps along `threadIdx.x` first. Mapping `x` to columns means the 32 threads of a warp read 32 adjacent floats in
  one row, which the hardware serves in a few wide transactions. Swap the mapping and each warp reads down a column, touching 32 different
  rows: often several times slower ([4.7](/learn/m04/coalesced-vs-strided)).
</Callout>

## Choosing a block size

- Make it a **multiple of 32** (the warp size), or the last warp in each block runs partly empty.
- **128–256 threads** is a good default. It gives the scheduler several warps per block without hitting resource limits ([2.5](/learn/m02/occupancy-latency-hiding)).
- The hard limits: 1,024 threads per block; grid up to $2^{31}-1$ blocks in x and 65,535 in y and z.

In LLM kernels, the grid usually mirrors the data: one block per token row for RMSNorm, a grid of (heads × batch) blocks for decode
attention, a 2D grid of output tiles for a matmul.
